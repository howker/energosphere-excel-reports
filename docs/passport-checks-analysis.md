## Коэффициенты

Исходник `MeaCoeff` подтверждает выбор действующей установки по дате и
приоритет минимальной фазы (`NULL` считается 0). Затем функция получает
первичный и вторичный номиналы через `MAT_PT_KTR` и `Meter_AttributeFlt`,
которая учитывает атрибуты экземпляра. Положительные номиналы делятся.
При отсутствующем или неположительном номинале функция возвращает 1;
это запасное значение, а не доказательство наличия трансформатора 1/1.

`MeaCoeffStr` формирует отношение из числовых номиналов. При вызове с
конкретным ID экземпляра сохраняется возможность проверить каждый ТТ
отдельно. Если указать установочный узел, выбирается минимальная фаза.

Для нашего примера ожидаем ТТ 50/5, коэффициент 10; ТН 10000/100,
коэффициент 100, общий коэффициент 1000. Это ожидание по присланным
атрибутам, выполнение штатного расчёта ещё проверяется запросом 05.
Исходники `MAT_PT_KTR`, `P_Type`, `DT_Intersect` включены в следующий экспорт.

Готовую строку `MeaModuleTypeName`, содержащую 30/5 для типа ТТ, не используем
как источник номиналов установленных экземпляров: их переопределение — 50/5.

## Время

| Показатель | Фактическое значение |
|---|---|
| UTC_Bias_Minutes | 180 |
| GetCurrentDate — часы базы | 2026-10-08T13:35:19.990 |
| GETUTCDATE | 2026-10-08T10:35:19.983 |
| GETDATE — часы сервера | 2026-10-08T14:35:19.990 |

Настройка базы соответствует UTC+3, серверные часы в момент снимка — UTC+4.
Это разные часы; при сравнении периодов установки используем часы базы,
как штатные функции. Эти значения не определяют сами по себе формат
хранения даты поверки.

`GPSToLocalTime` прибавляет **число часов из IsDayLight(дата)**.
`LocalTimeToGPS` вычитает это же число. В комментарии названы абсолютное
и сезонное время. Функции не прибавляют UTC_Bias. Название GPS здесь
не доказывает хранение UTC или применение поправки на високосные секунды.

Значение 2021-08-04T23:00:00 и дата образца 05.08.2021 согласуются с
прибавлением одного часа, но правило ещё не подтверждено исходником
`IsDayLight`. В запросе 05 будут исходники и результаты преобразования
дат всех четырёх экземпляров. Нужно проверить сезонную логику и будущие
даты до переноса правила в Go. Текущую разницу серверных часов не
прибавляем к историческим датам автоматически.
Запрос также содержит отдельно помеченные синтетические проверки зимних,
летних и будущих дат. Они служат проверке функции и не являются полями паспорта.

## Шины

В РУ 48801 обнаружены две шины: **СШ1 (48804)** и **СШ2 (48805)**.
Присоединение 48803 находится непосредственно под РУ; в его основной
иерархии и в иерархии счётчика 48847 шина отсутствует.

ТН 48815 имеет непосредственного родителя **СШ2**. Это исправляет
предварительное предположение, что родитель 48805 — другое присоединение.
ТН используется несколькими присоединениями через отдельные ссылки;
поэтому его шина не становится автоматически родителем целевого
присоединения. В шаблоне записана СШ1, но эта принадлежность не подтверждена
полученными данными старой копии. Поле шины оставляем отсутствующим;
выбор по близости названия или совпадению РУ недопустим.

Полное имя файла продолжает формироваться по прямой цепочке родителей
присоединения. СШ2 из цепочки ТН в имя не добавляем.

## Следующий шаг

`sql/05-export-passport-validation.sql` проверит готовые коэффициенты и
преобразованные даты, а также выгрузит исходники вспомогательных функций.
Результат — `PassportValidationXml`; сохранить как
`CSD_Astrakhan_passport_validation.xml`.

Скрипт записывает только локальные табличные переменные. Текст использует
синтаксис SQL Server 2008 R2 и проверенные столбцы таблиц; на сервере ещё
не выполнялся. В отличие от метаданных, числовые и датовые секции вызывают
штатные функции. Определения их непосредственных вызываемых функций
изучены; оставшиеся помощники выгружаются для проверки точного поведения.
