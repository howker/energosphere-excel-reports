Обновление после третьего экспорта: фактические значения и решение брать
все данные из Энергосферы зафиксированы в `passport-48803-analysis.md`.
Текущая база — старая тестовая копия; старые поверки ожидаемы.

Анализ файла `C:\Users\serg\Desktop\PassportDiscoveryXml1.xml`, выгруженного
08.10.2026 в 10:03:40 UTC. XML читается полностью: 15 определений функций,
124 типа узлов, 60 атрибутов оборудования и три найденных узла дерева.
Выводы ниже основаны на справочниках и исходниках функций из этой базы.
Фактические значения оборудования ещё нужно получить третьим запросом.

Требование пользователя к имени выходного файла: полная цепочка присоединения
с верхнего уровня, разделитель — пробел. Пример базового имени:
`Астраханский ГПЗ ГПП-1 ЗРУ 6кВ№1 яч.1 РП-17`.
Имя одного конечного узла недостаточно. Третий запрос дополнительно экспортирует
упорядоченную цепочку прямых родителей `connection_path` и её текст
`full_connection_path`. До получения результата не отбрасываем уровни дерева
по предположению и не заменяем их названия локальными сокращениями.

## Как база выбирает оборудование

`Points` хранит дерево, `PointRelations` — связи с предками и дополнительные
связи. Типы 21 и 149 обозначают счётчик и точку поставки, 81 — ТТ,
85 — ТН, 255 — ссылку на другой узел через `ID_Ref`.

`MeterMountHist` связывает узел с экземпляром `MeterInfo`. Штатные функции
считают запись действующей при `DT_Mount <= дата AND дата < DT_Dismount`.
В третьем запросе используется тот же интервал. NULL в дате демонтажа
не подменяется бесконечностью: сначала нужно проверить реальные записи.

`Meter_Transformators` получает узел счётчика и ищет ТТ/ТН с тем же родителем,
включая ссылки на трансформаторы. Поэтому нельзя без проверки передавать
в эту функцию ID присоединения: его родитель — РУ, а родитель счётчика
может быть присоединением. Третий запрос сначала находит узлы счётчиков.

`MeterInfo.ID_ModuleType` соединяется с `ModuleTypes.ID_Type` в штатном коде.
Атрибуты экземпляра и типа находятся в `MeterAttributes`. Функции
`Meter_AttributeFlt` и `Meter_AttributeStr` сначала берут непустое значение
экземпляра, затем значение типа; числовой ноль считается значением.
Для строкового атрибута 6 название типа берётся из `ModuleTypes.NameType`.
У `Meter_AttrList` поведение при NULL отличается: наличие строки экземпляра
может скрыть строку типа. Для генератора нужно выбрать поведение осознанно.

## Почему готовые строки функции нельзя сразу записать в шаблон

`GetObjectAttributeDT(1, ...)` принимает **ID узлов Points**, хотя тип
объекта 1 называется «Счётчик». Передача ID экземпляра из `MeterInfo`
даст другой смысл или пустой результат.

Функция `Meter_Transformators_MeaInfo` собирает строки вида
`Фаза A: значение, Фаза C: значение`. Шаблон содержит другой формат
разделителей и дат. Название из `MeaModuleTypeName` дополнено напряжением,
коэффициентом и классом точности; оно отличается от простого `NameType`.
Для генератора лучше сохранять отдельные записи оборудования и форматировать
их по правилам шаблона, используя готовые строки базы для контрольной сверки.

`IntToPhase` задаёт 1=A, 2=B, 3=C. Значение 0 требует отдельной обработки.
Не следует автоматически приписывать общему ТН фазу A.

В коде `GetObjectAttributeDT` нет удаления строк, у которых все значения NULL,
несмотря на описание в комментарии. Генератор должен проверять сами значения.

Часы базы берутся через `GetCurrentDate`, которая учитывает `GetUTCBias`.
Время сервера `GETDATE()` нельзя автоматически считать эквивалентным.

## Следующий экспорт

Выполнить `sql/03-export-one-passport.sql` и сохранить XML как
`CSD_Astrakhan_one_passport.xml`. Запрос возвращает:

- ветку присоединения 48803, предков и связанные узлы;
- цепочку названий от верхнего родителя до присоединения для имени файла;
- историю установки счётчиков, ТТ и ТН с признаком действующей записи;
- экземпляры оборудования, типы и выбранные атрибуты экземпляров/типов;
- дополнительные свойства узлов и контрольные значения штатных функций;
- исходники пяти вспомогательных модулей, включая расчёт коэффициентов.

Все INSERT пишут в локальные табличные переменные. Запрос не изменяет
таблицы базы; архивы `PointMains` и `Mains` в тексте запроса не используются.
Ограничения — глубина дерева 32, до 300 узлов ветки, 600 связанных узлов
и 2000 записей установки. При превышении запрос останавливается с ошибкой.
Размер итогового XML заранее не гарантируется; область данных ограничена
одним присоединением и его оборудованием.

Полученный снимок описывает оборудование на дату выполнения. Прошлая история
установки сохранена отдельно для проверки отличий от образца. Это не
транзакционно согласованная резервная копия: часть штатных функций использует
NOLOCK, а несколько чтений могут увидеть изменения во время экспорта.

Запрос проверен статически по присланной схеме и определениям функций.
На SQL Server он ещё не выполнялся. После получения результата можно
подтвердить карту всех 23 входных полей и правила заполнения по фазам.
